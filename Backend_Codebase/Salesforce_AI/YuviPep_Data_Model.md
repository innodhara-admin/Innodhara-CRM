# YuviPep AI Sales Platform — Data Model & Tables Reference

## The Single Source of Truth for Every Table and Field

This document defines every table the platform stores, field by field. It is the companion to **"30 Real-Life Workflows"** — whenever a workflow shows something in brackets, like (`action_items.assignee_id`), the full definition lives here. Together, the two documents are a complete specification of the product.

Every table in this document follows the same format: first a short explanation of **what one row means, who creates it, and who reads it**, then a drawn table listing **every field with its type, its meaning, and a concrete example**. The examples follow the same story as the workflows document: Vivekananda Group (VG), its managing director Mr. Harish Singhania, and the YuviPep team (Akash the sales lead, Rahul the salesperson, Meera, Sourav, Mithun and the others).

# 1. Conventions That Apply Everywhere

**Fields every table has (not repeated below).** Every table automatically has these four fields, so they are not listed again in each table:

| Field | Type | Meaning |
|---|---|---|
| id | id | A unique identifier for the row, generated by the system. |
| org_id | link → organisations | Which organisation this row belongs to. See the isolation rule below. |
| created_at | date-time | When the row was created. |
| updated_at | date-time | When the row was last changed. |

**The isolation rule.** The platform serves many organisations. Every row is stamped with `org_id`, and every query filters on it, so one organisation's rows can never be returned to another. On PostgreSQL a second, independent fence is added by applying `scripts/postgres_rls.sql`, which makes the database itself refuse cross-organisation rows even if application code has a bug; the development default is SQLite, where the application-level scoping and the row-level `org_id` stamp are the protections in force. Files are stored under per-organisation folders (`orgs/{org_id}/...`), and the AI memory keeps one namespace per organisation. Nothing ever crosses between organisations.

**The type vocabulary** used in the field tables:

| Type | Meaning |
|---|---|
| id | a system-generated unique identifier |
| link → *table* | the id of a row in another table (a relationship) |
| text | a short piece of text (a name, a title, an address) |
| long text | free text of any length (a note, an email body, a transcript) |
| number | a whole or decimal number |
| money | an amount in the organisation's currency |
| yes/no | true or false |
| date / time / date-time | a calendar date, a clock time, or both |
| choice | one value from a fixed list — the allowed values are always listed in the Meaning column |
| list | several values in one field (e.g. a list of task ids) |
| structured | structured data (JSON) — the exact shape is shown in the Example column |

**Status badges** on table headings:

- **[CORE]** — a foundation table; almost everything links to it.
- **[NEW]** — introduced by the workflow design (the project layer, the event loop, the people model).
- **[EXPANDED]** — a table from the earlier design that gains new fields for the workflows. New fields are marked with ✚.
- Tables with no badge come from the earlier design and are kept as they are.

**"user id or 'ai'".** Many fields record who did something. They hold a user id when a person did it, or the literal value `"ai"` / `"system"` when an engine did it. This makes every action attributable — human or machine.

**Nothing invented by AI touches money.** Prices always come from `pricing_tables`; special prices always come from a recorded human approval (`approvals`). The AI only writes the words around the numbers, never the numbers.

# 2. Platform & People

## 2.1 `organisations` [CORE]

One row = one company using the platform (YuviPep, and later others). It is the parent of every other record: every table in this document carries this row's id as its `org_id`. Rows are created only by the platform Super Admin during onboarding; Org Admins edit their own row's branding.

**In simple words:** Think of the platform as one big building and each organisation as a locked office inside it. This table is the list of offices. Every other record in the system is stamped with the office it belongs to, so YuviPep's papers can never land on another company's desk. When a new company joins, the platform owner adds one row here; afterwards that company's own admin can change its logo and colours, but nobody else can touch it.

| Field | Type | Meaning | Example |
|---|---|---|---|
| name | text | The company's display name, shown in the app and on documents. | "YuviPep" |
| slug | text | A short, unique, machine-friendly code for the organisation. Used in URLs and file paths. | "yuvipep" |
| email_domain | text | The company's email domain. A person logging in with an email on this domain belongs to this organisation. | "@yuvipep.com" |
| logo_url | text | Where the company logo file lives. Printed on proposals and reports. | "orgs/yuvipep/logo.png" |
| brand_colors | structured | The company's colours, used to style the app and generated documents. | {"primary":"#1F3A5F","accent":"#E8A13D"} |
| is_active | yes/no | Switched off when an organisation leaves the platform. A deactivated organisation's users cannot log in. | true |

## 2.2 `org_settings` [EXPANDED]

One row per organisation — the behaviour dials. This is how the same platform behaves differently for each company: how strictly it reviews, how hard it chases, when it stays quiet, and how it talks to clients. Only the Org Admin can change these values. Every engine reads this table before acting.

**In simple words:** This is one company's control panel — a page of switches and dials. It decides how the app behaves for that company: how hard it chases overdue work, what counts as working hours, how many times a client may be nudged, when the weekly report goes out, and whether work may start before the advance is paid. It never changes what the system can do — only how strictly, how often, and when it does it for this company.

## 2.3 `users` [EXPANDED]

One row = one staff member who logs in. The email is the identity and decides the organisation; the role decides what they may do. Roles: `org_admin` (sets up programs, pricing, staff, rules), `sales_agent` (meets clients, records meetings), `sales_lead` (manages sales agents, approves client messages), `operations_agent` (delivers trainings, builds content), `operations_lead` (owns delivery, teams, logistics). One special platform-level role, `super_admin`, has no org_id, creates organisations, and can never read any organisation's sales data.

**In simple words:** The staff list. One row per employee who can open the app. A person's email is their identity and decides which company they belong to; their role decides which buttons they can press. Their leave dates and their task capacity also live here, so the AI always knows who is available, who is away, and who is already full.

## 2.4 `user_skills` [NEW]

One row = one skill of one person, with a level. This is the heart of task assignment: `action_items.required_skill` is matched against these rows to build the candidate list. Skills are a free vocabulary each organisation defines for itself; the Org Admin or a lead maintains them, and leads adjust levels when reality proves them wrong.

**In simple words:** A simple list of what each person is good at — like a skills column on a team whiteboard: "Meera — curriculum design: expert." When a new task needs a certain skill, the AI reads this list to work out who could do it and how well.

| Field | Type | Meaning | Example |
|---|---|---|---|
| user_id | link → users | Whose skill. | Sourav |
| skill | text | The skill name, matched exactly against `action_items.required_skill`. Examples of one org's vocabulary: android, robotics, curriculum_design, scheduling, proposals, english_writing, hindi, invoicing, photography, teaching, logistics, negotiation, field_sales. | "android" |
| level | choice | `basic` / `good` / `expert`. Expert beats good beats basic in candidate scoring. | "expert" |

## 2.6 `audit_log`

One row = one sensitive action, recorded forever: who did what, to which record, when. Written automatically on every login, send, approval, price change, deletion, settings change, and role change. Read by Org Admins for review and by the platform for security investigations. Nothing in this table can be edited or deleted.

**In simple words:** The security camera of the system. Every sensitive action — a login, a sent proposal, a price change, a deletion — is written down here permanently and can never be edited or erased. Whenever anyone asks "who did this, and when?", this table is the answer.

## 2.7 `idempotency_records`

One row = one already-processed request. Protects against double actions: if the app retries a request after a dropped connection (or a person double-taps Send), the system finds the same key here and does **not** send the email twice or create the task twice. Written and read by the API layer on every state-changing request; rows expire after a safe period.

**In simple words:** A guard against accidental double-clicks. If the network drops and the app repeats a request, or a person double-taps Send, this table recognises "we already did this one" and quietly ignores the repeat — so a client never gets the same email twice and a task is never created twice.

| Field | Type | Meaning | Example |
|---|---|---|---|
| key | text | A one-time code the app attaches to each request. If the same code ever arrives again, the system knows it is a repeat — not a new request. | "send-msg-7f3a..." |
| endpoint | text | Which operation it protected. | "POST /messages/send" |
| entity_id | id | The record the first, successful attempt created. A retry simply gets this same record back instead of creating a duplicate. | (message id) |
| at | date-time | When the first attempt happened. | — |

## 2.8 `llm_usage`

One row = one AI model call, with its cost. This is how the platform keeps AI spending visible and capped: rows are summed per organisation per month and checked against `org_settings.llm_monthly_budget_usd`; alerts fire before the budget is crossed. Written automatically by the model layer on every call; read by cost dashboards and budget alarms.

**In simple words:** The AI's expense diary. Every time the AI "thinks" (makes a call to the model), one row records what that moment of thinking cost. The rows are added up each month and compared with the company's AI budget, so the bill never comes as a surprise.

| at | date-time | When. | — |

## 2.9 `jobs`

One row = one background job (transcribe this meeting, build this plan, generate this report). Slow work never blocks the app: it is queued here, workers pick it up by priority, failures retry with growing waits, and a job that keeps failing lands in a dead-letter state that raises an alert — so nothing ever fails silently. Written by whatever queues the work; read by the worker pool and by the app's progress screens.

**In simple words:** The waiting line for slow machine work. Turning a 40-minute recording into text takes a while — instead of freezing the app, that work waits in this queue and background workers pick it up one by one. A failed job retries by itself, and one that keeps failing raises an alarm for a human instead of silently disappearing.

| Field | Type | Meaning | Example |
|---|---|---|---|
| type | text | Which kind of work. | "process_meeting" |
| payload | structured | The inputs the worker needs. | {"meeting_id":"..."} |
| status | choice | `queued` / `running` / `done` / `failed` (will retry) / `dead_letter` (gave up, alert raised). | "done" |
| priority | number | Lower number = served first. A person waiting on their screen always beats invisible background work. | 100 |
| attempts, max_attempts | number | How many tries so far, and the limit before dead-letter. | 1 / 4 |
| next_run_at | date-time | When the next attempt may start. Each failure waits longer before retrying (for example 1 minute, then 5, then 25), so a struggling service gets room to recover instead of being hammered. | — |
| last_error | long text | The most recent failure reason. | empty |
| result | structured | What the job produced, for the app to show. | {"action_items":5} |
| started_at, finished_at | date-time | Timing of the last run. | — |

## 2.10 `assistant_turns` [NEW]

One row = one thing said in a conversation with the assistant — either what the person typed or dictated, or the reply that came back. Rows are grouped by `session_id` (one chat thread) and belong to one person in one organisation. Written by the Orchestrator after each completed command; read at the start of the next command, so the assistant can understand "make it warmer", "send it to her" and "tell me about the second one" instead of treating every sentence as if it were the first thing ever said to it.

Only the **words** are kept. The tools an agent called, the results they returned and the ids of the records touched are deliberately not stored: they belong to the request that made them, and re-using a stale id later would let the assistant act on a record whose permissions may since have changed. When the assistant needs a fact again, it looks it up again — freshly scoped and freshly permission-checked.

A conversation is working memory, not a record. The organisation's durable history lives in `audit_log`, `ai_decisions` and `progress_events`; these rows are trimmed to the most recent turns per conversation, dropped entirely after 90 days, and removed when a person is erased under a data-subject request.

**In simple words:** What you and the assistant just said to each other. Without it, every message starts from zero — which is why an assistant that "forgets" the sentence before feels so lifeless. Only the words are kept, never the keys to anything; and the chat is cleared out on a timer, because a scratchpad should not quietly become a filing cabinet.

| Field | Type | Meaning | Example |
|---|---|---|---|
| session_id | text | Which conversation this turn belongs to — one chat thread, chosen by the app. | "9f1c…" |
| user_id | link → users | Whose conversation it is. A conversation is private to this person, even from colleagues in the same organisation. | Rahul |
| seq | number | Position in the conversation. Needed because a question and its answer are saved in the same instant, and a clock alone could put them the wrong way round. | 7 |
| role | choice | `user` (what the person said) / `assistant` (what came back). | "user" |
| content | long text | The words themselves. | "make it warmer, and mention the December dates" |
| agent | text | Which specialist answered — empty on the person's own turns. | "proposal" |

## 2.11 `device_tokens` [NEW]

One row = one mobile device registered to receive push notifications for one person. A person may hold several (phone and tablet); a row is upserted when the app registers a token and deleted when the provider reports the token dead, or when the person signs out on that device.

Push is only the doorbell. The notifications row is always the source of truth and the app's notification screen reads that, not this table — so a missing or stale token can delay a buzz but can never lose the notification itself.

**In simple words:** the list of phones the app is installed on, so the system knows where to ring. Losing a row here means a phone stops buzzing; it never means a message is lost, because the message itself lives in the notifications table.

| Field | Type | Meaning | Example |

| user_id | link -> users | Whose device this is. | Rahul |
| fcm_token | text | The provider's address for this installation. Unique across the platform: if the same token reappears for a different person, the row moves to them rather than being duplicated. | "fVx9...": |

# 3. Clients & Relationships

## 3.1 `leads` [EXPANDED]

One row = one client we want to win (or have won). **The lead is the relationship; the work lives in `projects`.** Anything true about the client forever — its contacts, its preferences, its history — hangs off the lead; one lead can hold many projects at once and over the years. Created by a salesperson (by voice, type, or card scan); its `state` summarises where the relationship stands, and only humans confirm state changes (the system may suggest them).

**In simple words:** One row per client we want as a customer — the relationship card. It remembers where the client is, how we found it, which salesperson owns the relationship, and where things stand: just met, actively talking, gone quiet, won, or "not this year." The actual pieces of work for a client live in projects; the client itself, and everything permanently true about it, lives here.

| Field | Type | Meaning | Example |
|---|---|---|---|
| name | text | The client's name. | "Vivekananda Group" |
| address, city, region | text | Where it is. | "Salt Lake, Kolkata, WB" |
| website | text | The client's site, if known. | "svs.edu.in" |
| source | text | How we found them: referral, expo, cold call, inbound... | "managing director called us" |
| state | choice | Where the relationship stands: `open` (contact made, no real talk yet) / `active` (in regular talks) / `cold` (gone quiet) / `execution_in_progress` (deal agreed, work being set up) / `client_execution_in_progress` (program running in the client) / `closed` (delivered and paid) / `lost_for_now` (didn't win this time — may retry). | "active" |
| is_important | yes/no | The "Active and Important" flag for high-value leads that need extra focus. | false |
| owner_id | link → users | The accountable salesperson for the relationship. | Rahul |
| notes | long text | Free-running context. | "Managing Director is technical, likes detail" |
| last_activity_at | date-time | The last time anything at all happened with this client. When this date gets older than `org_settings.lead_cold_after_days`, the system suggests marking the lead `cold`. | — |
| suggested_state, suggested_state_reason | choice + long text | A system-suggested state move waiting for a human yes. | "cold", "no reply for 30 days" |
| ✚ lost_reason | choice | Why we lost, structured so it can be analysed: `budget_timing` / `chose_competitor` / `no_need` / `other`. | "budget_timing" |
| ✚ revival_date | date | When to wake this lead again. The Sync Engine fires a revival card a week before. | 2027-04-01 |
| ✚ revival_context | long text | AI-written wake-up brief: what they liked, who the champion was, what objection killed it, what to offer next time. | "Liked content plan; objection was FY budget only; coordinator was champion; quote group discount" |
| revival_fired_at | date + time | When the revival card was raised, so a sleeping lead is woken exactly once. Empty until the sweep fires seven days before revival_date. | 2026-11-24 09:00 |

**State transitions:** open → active → execution_in_progress → client_execution_in_progress → closed. Any talking state ↔ cold (no reply / re-engages). Anything → lost_for_now. lost_for_now → open/active on revival. Every change is recorded in `lead_state_history`.

## 3.2 `lead_state_history`

One row = one state change of one lead — the full journey, forever. Written automatically whenever `leads.state` changes; read by anyone asking "how did this client get here?"

**In simple words:** The client's journey, written down step by step. Every time the relationship moves ("open" became "active"), one row records the move, the reason, and who confirmed it — so anyone can retrace exactly how we got from first phone call to signed deal.

| Field | Type | Meaning | Example |

# 9. How the Tables Connect

```
organisation
 ├── users ── user_skills, resource_bookings, assistant_turns (private chat)
 ├── org_settings, approval_rules, playbooks, vendors
 └── leads (the client relationship)
      ├── contacts, consent_records, client_intelligence, memory_chunks
      ├── followups (pre-project reminders)
      └── projects (the work)  ←── parent_project_id (chain deals)
           ├── project_members, stakeholders
           ├── action_plans (versioned) ── action_items ── assignments, reminders
           ├── client_commitments, conflicts, incidents
           ├── meetings ── transcripts
           ├── proposals ── proposal_revisions
           ├── deliverables, invoices ── payments
           ├── threads ── outbound_messages ── message_delivery_log
           │            └─ inbound_messages
           ├── approvals
           ├── progress_events (the heartbeat)
           ├── ai_decisions (the explanations)
           └── digests (the summaries)
```

Three reading rules:

1. **The lead is the relationship, the project is the work.** Anything true about the client forever (contacts, intelligence, memory) lives on the lead; anything true about one engagement (plan, team, money, conversation) lives on the project. Conversations may begin before a project exists: `threads` always carry `lead_id` and `contact_id`, and gain `project_id` + `stakeholder_id` when a project is born.
2. **Versions, never edits.** Plans, pricing, templates, playbooks, proposals, and deliverables all version. What was sent yesterday can always be reproduced exactly.
3. **Every arrow is also stamped.** Every row carries `org_id` directly, so isolation between organisations holds even without following the links.
